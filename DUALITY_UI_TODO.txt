2.  CONCEPTUAL MISMATCH — UI Model vs Backend Model
----------------------------------------------------------------------

The current UI and the LOSM backend operate on fundamentally different
mental models. This is the most important gap to address.

UI's current model:
  "User messages an Architect agent → Architect plans and delegates to
   Builder agent → Builder generates files → File tree changes."

LOSM backend model:
  "User intent → WorkRequest → PlanIR → CritiqueIR → SpecIR → ExecutionIR
   → ValidationIR. Each step is a typed, immutable artifact. State machine
   governs transitions. Human approval gates at PLAN_APPROVAL_GATE."

The UI's "Architect" role maps loosely to (PLAN_GENERATION + PLAN_REVIEW).
The UI's "Builder" role maps loosely to (SPEC_GENERATION + EXECUTION).
But the current implementation has NO artifact types, NO state machine,
NO approval gates, NO validation step, and NO persistence.

Two possible alignment strategies exist (decision needed):

  STRATEGY A — "UI drives LOSM operator IDE"
    Recast the UI as the Phase 11 Operator IDE from the LOSM
    implementation plan. "Architect" and "Builder" become LOSM actor
    roles within that IDE. The chat metaphor is replaced (or augmented)
    by artifact inspection, state timeline, and transition controls.
    The current mock is kept as an early visual prototype but re-architected.

  STRATEGY B — "Two separate interfaces"
    Keep the current UI as an architect/builder chat IDE (a front-end
    for a different workflow). Build a separate LOSM operator IDE
    (or add a tab/mode) that shows the state machine, artifacts, and
    transition controls. This is more work but avoids forcing the
    architect/builder metaphor into the LOSM state machine.

Recommendation: Strategy A (single unified operator IDE). The UI already
has the right layout (chat left, execution right, file tree, terminal,
workspace). The main work is replacing the mock service and recasting
the components to use LOSM types.

7.  MOCK-TO-REAL SERVICE ADAPTER PATTERN
----------------------------------------------------------------------

Define a common interface so mocks and real API adapters can coexist.
Keep mocks available for frontend development when backend is behind.

    interface LOSMApiService {
      // WorkRequest
      createWorkRequest(intent: string, metadata?: Record<string, any>): Promise<WorkRequest>;
      getWorkRequest(id: string): Promise<WorkRequest>;
      listWorkRequests(): Promise<WorkRequest[]>;

      // Plan
      generatePlan(wrId: string): Promise<PlanIR>;
      getPlan(planId: string): Promise<PlanIR>;

      // Critique
      critiquePlan(planId: string): Promise<CritiqueIR>;
      getCritique(critiqueId: string): Promise<CritiqueIR>;

      // Spec
      generateSpec(planId: string): Promise<SpecIR>;
      getSpec(specId: string): Promise<SpecIR>;

      // Execution
      execute(specId: string): Promise<ExecutionIR>;
      getExecution(executionId: string): Promise<ExecutionIR>;
      getExecutionTrace(executionId: string): Promise<TraceEvent[]>;

      // Validation
      validate(executionId: string): Promise<ValidationIR>;
      getValidation(validationId: string): Promise<ValidationIR>;

      // State
      getCurrentState(wrId: string): Promise<string>;
      getTransitionHistory(wrId: string): Promise<TransitionEvent[]>;
    }

    // Implementations:
    class MockLOSMApiService implements LOSMApiService { ... }
    class HttpLOSMApiService implements LOSMApiService { ... }

    // Selection based on backend availability:
    const api: LOSMApiService =
      import.meta.env.VITE_USE_MOCK === 'true'
        ? new MockLOSMApiService()
        : new HttpLOSMApiService();

9.  SUMMARY OF WHAT MATTERS
----------------------------------------------------------------------

The current UI is a visually polished mock of a dual-agent IDE that does
not yet connect to the LOSM backend. The main work is:

  1. **RECAST THE UI COMPONENTS** to show LOSM artifacts instead of
     architect/builder chat (Phase 1).
  2. **EXPAND THE MOCK SERVICE** to cover all LOSM types so the UI can
     drive the full intent→validation lifecycle even without the backend
     (Phase 0).
  3. **SYNC THE TYPES** between TypeScript and Pydantic models so
     field names, shapes, and semantics match exactly.
  4. **WIRE TO THE REAL BACKEND** phase-by-phase as the backend
     implementation catches up (Phases 2-8).
